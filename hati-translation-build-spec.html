HaTi Bilingual Build Spec

How to add an English ⇄ Swedish language switch to HaTi (Mkataba CLM), using the proven translation architecture from the VCFO Terminal.

Source pattern: youngmbg21-cmyk/vcfo Target repo: youngmbg21-cmyk/mkataba-clm Author: Young Mbagaya Date: 28 July 2026

Part A How the VCFO translation system works (plain English)

VCFO does not run text through a translation service. Instead, every piece of English text in the app was written down twice — once in English, once in Swedish — in one big organised list inside the app itself. A small switch decides which column of that list the app reads from. Six building blocks make this work:

BlockWhat it isEveryday analogy
1. The dictionary One JavaScript object called STRINGS with two halves: en and sv. Every label, button, heading, and message has a short nickname (a "key") like tab_company, and each half gives that key its text in one language. VCFO's dictionary has roughly 180 keys per language. A restaurant menu printed in two columns — same dishes, same order, English on the left, Swedish on the right.
2. The memory of your choice A variable appLang holds the current language ('en' or 'sv'). It is saved to localStorage (a small notepad the browser keeps for each website), so the app remembers your language next time you visit. A sticky note on your fridge: "This household speaks Swedish."
3. The lookup helper A tiny function t(key). Give it a nickname, it hands back the text in the current language. If a Swedish translation is missing, it quietly falls back to English instead of showing a broken label. A waiter who reads the correct menu column for you — and reads the English column if a Swedish line was left blank.
4. Labels on the furniture Every fixed piece of text on the page carries a small tag in the HTML: data-i18n="key_name". This tag doesn't change how anything looks — it just marks "this text is translatable, and here is its nickname." Price stickers on shop shelves. The sticker says which product it belongs to, so restocking staff know exactly what goes where.
5. The switch sweep One button flips the language. It calls applyLanguage(), which walks through the whole page, finds every tagged element, and swaps its text using the lookup helper — instantly, with no page reload. Flipping every menu on every table in the restaurant at once, in one pass through the room.
6. The AI speaks the same language When the app asks Claude to write an analysis, it adds one line to the request: "Write the entire response in Swedish" (or English). So AI-generated content follows the switch too — the dictionary only covers fixed text; the AI covers everything it writes fresh. Telling a guest speaker before they walk on stage: "The audience tonight is Swedish — present in Swedish."
Why this approach is right for HaTi: it's a zero-dependency pattern — no libraries to install, no build step, no external translation service, no cost per page view. It fits your single-file, no-build-step convention exactly, and translations are reviewed by a human once instead of machine-translated live (important for a contract platform where wording is legally sensitive).

Part B The architecture, with the actual code pattern

These five code blocks are the complete engine, adapted from VCFO with HaTi naming. Claude Code should replicate this structure — not invent an alternative.

B1. Language state + saved preference

Placed near the top of the app's JavaScript. Reads the saved choice; defaults to English.

// ============================================================
// INTERNATIONALISATION — EN / SV
// ============================================================
let appLang = 'en';
try { appLang = localStorage.getItem('hati_lang') || 'en'; } catch(e) {}

The try/catch means: if the browser blocks saving (some private-browsing modes do), the app still works — it just forgets the choice between visits.

B2. The dictionary

One flat object, snake_case keys (matches your existing record conventions), grouped by screen with comment headers. English is the master list; Swedish mirrors it key-for-key.

const STRINGS = {
  en: {
    // Topbar
    lang_toggle:       '🇸🇪 Svenska',   // button shows the OTHER language
    nav_contracts:     'Contracts',
    nav_templates:     'Templates',
    btn_new_contract:  '+ New Contract',
    status_draft:      'Draft',
    status_signed:     'Signed',
    // ... every fixed label in the app ...
  },
  sv: {
    lang_toggle:       '🇬🇧 English',
    nav_contracts:     'Avtal',
    nav_templates:     'Mallar',
    btn_new_contract:  '+ Nytt avtal',
    status_draft:      'Utkast',
    status_signed:     'Signerat',
    // ... same keys, same order ...
  }
};

The toggle button's own label is a dictionary entry too — in English mode it shows "🇸🇪 Svenska" (the destination, not the current state).

B3. The lookup helper — with fallback and fill-in-the-blank values

This is an upgraded version of VCFO's helper. It does two jobs: fetch the text in the current language, and fill in any blanks like {days} or {name} with real values.

function t(key, vars) {
  let s = (STRINGS[appLang] || STRINGS.en)[key] || STRINGS.en[key] || key;
  if (vars) {
    Object.keys(vars).forEach(k => {
      s = s.split('{' + k + '}').join(vars[k]);
    });
  }
  return s;
}

Three safety nets: unknown language → English; missing Swedish key → English; key missing everywhere → show the key name itself (so a gap is visible during testing, never a blank).

How the fill-in-the-blank works in practice — the dictionary holds the sentence with a placeholder, and the code supplies the value:

// In the dictionary:
expiry_notice: 'Contract expires in {days} days',        // en
expiry_notice: 'Avtalet löper ut om {days} dagar',        // sv

// In the code:
const msg = t('expiry_notice', { days: 14 });

Why this matters: word order differs between languages. If code glues sentences together piece by piece ("Contract expires in " + 14 + " days"), the Swedish version comes out garbled. With placeholders, each language writes its sentence naturally and the value drops in wherever that language needs it.

Plurals: where a count changes the wording (1 avtal / 2 avtal, 1 day / 2 days), use two keys — a _one and an _many variant — and pick between them in code with a simple count === 1 check. Don't build anything cleverer than that.

B4. Tagging static text in the HTML

<div class="tab" data-i18n="nav_contracts">Contracts</div>
<button data-i18n="btn_new_contract">+ New Contract</button>

The English text stays inside the tag as the default — the page reads correctly even before any JavaScript runs. Input placeholders (the grey hint text in empty boxes) can't use this tag directly; they're set individually inside applyLanguage().

B5. The toggle and the sweep

function toggleLanguage() {
  appLang = appLang === 'en' ? 'sv' : 'en';
  try { localStorage.setItem('hati_lang', appLang); } catch(e) {}
  applyLanguage();
}

function applyLanguage() {
  // 1. The toggle button itself
  const btn = document.getElementById('langToggleBtn');
  if (btn) btn.textContent = t('lang_toggle');

  // 2. Every tagged element on the page
  document.querySelectorAll('[data-i18n]').forEach(el => {
    const val = t(el.getAttribute('data-i18n'));
    if (!val) return;
    // Use innerHTML only when the string genuinely contains HTML;
    // plain textContent is safer everywhere else.
    if (/<[a-z]/i.test(val)) {
      try { el.innerHTML = val; } catch(e) { el.textContent = val.replace(/<[^>]+>/g, ''); }
    } else {
      el.textContent = val;
    }
  });

  // 3. Placeholders and other special cases, set one by one
  const search = document.getElementById('contractSearch');
  if (search) search.placeholder = t('search_placeholder');
}

B6. Dynamic text built by JavaScript — everything goes through the dictionary

Text that JavaScript assembles on the fly (status messages, table rows, alerts, toasts) can't be tagged in HTML — it doesn't exist yet when the page loads. The rule for HaTi is simple: every piece of it, short or long, is a dictionary key, fetched with t() at the moment the text is built. Because rendering functions re-run when data changes, they pick up the current language automatically.

Deliberate improvement over VCFO: VCFO scatters long sentences through its code as inline either/or statements (isSv ? 'svenska...' : 'english...'). Do not replicate that pattern in HaTi. It works, but it makes translations impossible to audit — you can never see in one place whether everything is covered, and a Swedish reviewer would have to read the entire codebase. In HaTi, one hundred percent of user-visible text lives in STRINGS, so the dictionary is the single, complete, reviewable list. If a sentence needs a value inserted, use a {placeholder} as shown in B3 — never build sentences by gluing text fragments together in code.

B7. Making the AI follow the language switch

Wherever HaTi builds a prompt for Claude (via the Cloudflare Worker), inject a language instruction based on the current setting — this is exactly what VCFO does:

const lang = appLang === 'sv' ? 'sv' : 'en';
const langNote = lang === 'sv'
  ? 'Skriv hela svaret på svenska — all löptext, alla punkter, alla rubriker. Behåll JSON-nycklarna oförändrade.'
  : 'Write the entire response in English. Keep the JSON keys unchanged.';
// ...append langNote to the end of the prompt string...

The crucial detail: when the AI returns structured data (JSON), only the human-readable values switch language — the field names stay in English so the app can still read them.

B8. Switch it on at startup

document.addEventListener('DOMContentLoaded', () => {
  applyLanguage();   // restores the saved language before the user sees anything
  // ...rest of app initialisation...
});

Part C Build instructions for Claude Code — apply this to HaTi

Claude Code: implement the architecture above in the mkataba-clm repository. Work in the phases below, in order. Do not substitute a library-based i18n framework — replicate the vanilla pattern exactly, matching the repo's existing no-build-step, single-file conventions.

0

Survey before touching anything

Read the HaTi codebase first. Produce a short inventory: (a) every screen/view, (b) where static UI text lives, (c) every function that builds text dynamically, (d) every place a prompt is sent to the AI. Write this inventory to I18N_INVENTORY.md before writing any code. This becomes the master key list.

1

Install the engine

Add the code from B1, B3, B5, and B8 near the top of HaTi's script section: the appLang state with localStorage key hati_lang, the t() helper, toggleLanguage(), applyLanguage(), and the startup call. Add a language toggle button to the topbar with id langToggleBtn, styled to match existing header buttons.

2

Build the English half of the dictionary

Walk every screen from the inventory. For each fixed text element, invent a flat snake_case key with a screen prefix (nav_, btn_, status_, contract_, template_, party_, sign_, etc.), add it to STRINGS.en, and tag the HTML element with data-i18n="key". Group keys with comment headers per screen. The English text stays in the HTML as the default.

3

Write the Swedish half

Mirror STRINGS.en into STRINGS.sv, same keys, same order, same comment grouping. Translation register: professional business Swedish as used in Swedish contract and legal software (avtal, motpart, mall, signera, giltighetstid, uppsägningstid — not casual phrasing). Where a term is legally loaded, prefer the term Swedish contract tools like Oneflow use. Flag any translation you are uncertain about with a // TODO verify comment rather than guessing silently.

4

Convert dynamic text — dictionary only, no exceptions

Go through every rendering function from the inventory. Replace every hard-coded string — short labels and full sentences alike — with t('key') calls, adding keys to both language halves as you go. Sentences containing values use {placeholder} keys per B3; sentences whose wording changes with a count get _one / _many key pairs. Never use inline language ternaries and never concatenate sentence fragments in code. Toasts, empty states, confirmation dialogs, and error messages all count.

5

Wire the AI to the switch

In every function that builds a prompt for the Cloudflare Worker, append the language instruction from B7. Where the AI returns JSON, state explicitly in the prompt that keys stay in English and only values change language. Where AI output is stored (e.g., saved analyses), record which language it was generated in alongside the record, so old content isn't mistaken for the wrong language later.

6

Handle formats, not just words

Swedish mode should also format numbers and dates the Swedish way where they're displayed to users: use toLocaleString(appLang === 'sv' ? 'sv-SE' : 'en-GB') for amounts and toLocaleDateString for dates. Do not change how values are stored in Supabase — storage stays in neutral machine formats (ISO dates, plain numbers); only the display layer changes.

7

Test and document

Verify: toggle flips every visible label on every screen with no reload; refresh the page and the choice persists; a deliberately deleted Swedish key falls back to English (then restore it); AI responses arrive in the selected language; no console errors. Write SUMMARY.md covering what was changed, and log any untranslated leftovers or uncertain translations in BUGLOG.md, consistent with the existing overnight-loop output convention.

Guardrails for this build

Do not touch: the mobile/WhatsApp counterparty portal remains explicitly deferred — no work on it in this build. Do not modify the Supabase schema, the jurisdiction logic, or the role_profile logic. Do not add npm packages, build steps, or external i18n libraries. Do not machine-translate stored contract content — this build translates the app's interface, never the user's contract documents.
Keep language and jurisdiction separate: HaTi already treats jurisdiction as its own first-class field. Interface language is a display preference; jurisdiction is a legal property of a contract. A Kenyan user may view the app in Swedish and vice versa — never infer one from the other, and never let the language toggle change any contract data.
Future-proofing for a third language: this architecture extends by simply adding another block (e.g., sw: {...} for Swahili) to STRINGS and turning the toggle into a small cycle or dropdown. Nothing else changes. Structure the work so that adding Swahili later requires no refactor — but do not add it now.

Part D Acceptance checklist

The build is done when every box can be ticked:

  • A language toggle button sits in the topbar and shows the destination language ("🇸🇪 Svenska" when in English, "🇬🇧 English" when in Swedish).
  • One click switches every visible label, button, tab, heading, placeholder, and empty-state message on every screen — no page reload.
  • The choice survives closing and reopening the browser (saved as hati_lang).
  • Toasts, confirmation dialogs, and error messages appear in the selected language.
  • AI-generated analysis and suggestions arrive in the selected language; JSON keys stay in English.
  • Numbers and dates display in Swedish format in Swedish mode; stored data is unchanged.
  • A missing Swedish key shows the English text, never a blank or a crash.
  • Zero user-visible text exists outside the STRINGS dictionary — a search of the code finds no inline language ternaries and no glued-together sentence fragments.
  • Sentences with inserted values use {placeholder} keys; count-dependent wording uses _one / _many key pairs.
  • Contract content, jurisdiction, role_profile, Supabase schema, and the deferred mobile portal are untouched.
  • I18N_INVENTORY.md, SUMMARY.md, and BUGLOG.md exist and reflect the actual work.
