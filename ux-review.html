HaTi — the same two negotiations, run a third time on today's code

A user-experience review of the HaTi contract platform (repo youngmbg21-cmyk/mkataba-clm), based on reading and running the source at commit 01cfb6e, 26 July 2026. This is the third review. The first found eight problems; the second found two shipped bugs; all of that is now fixed and covered by automated checks. So this pass hunted for what is still true — and found five remaining frictions, each verified against the running code, none imagined. File and function names are given throughout so every claim can be checked.

The two people in the story

Wanjiru owns a small catering company in Nairobi. She drafted a 12-month supply agreement inside HaTi using the built-in "Raw Material Supply Agreement" template and the guided wizard (js/wizard.js, template RM in js/templates.js).

Erik is a procurement manager at a mid-size Swedish firm. In Scenario 1 he only uses Microsoft Word with tracked changes, over email. In Scenario 2 he works inside HaTi.

What the app actually has today

The honest inventory, from the code — not from what a contract tool usually has:

YES — One-click export of any contract as a real Word file, with an explained choice about pausing edits while it is out (openWordExportModal, js/docxwrite.js).
YES — Upload the counterparty's marked-up Word file onto the same contract; his tracked changes are counted and filed as a round in his name (js/wordflow.js).
YES — Accept or reject each change separately, see why they asked against each one, and reply on that change (reviewProposedRound, js/versioning.js).
YES — The counterparty edits clause by clause, with a "Why?" box per change, on one durable link that lasts the whole negotiation (js/views/portal.js).
YES — "Send updated version" genuinely emails him now, and says plainly when it could not (f24 proves it against a real server).
YES — The owner can see whether he has opened the current version, with one-click resend after 3 silent days (counterpartySeenHtml).
YES — A paper-signed scan files onto its own contract, history intact, honestly labelled "executed outside HaTi" (attachPaperSignature).
YES — Signing works even with no email service — required where a code can be sent, and labelled "not independently verified" where it cannot (f23).
NO — A Word export with the changes marked in red. The file is always clean text (js/docxwrite.js writes no tracked changes — verified). Erik must run Word's own Compare to see what moved.
NO — A wizard-drafted contract keeping its drafted look through negotiation. At the first accepted round the styled layout and fill-in fields are replaced by plain working text (verified by running acceptProposedRound on a template contract).
NO — A way to ask a question about a clause without proposing new text. Comments only travel attached to edits or to a whole round.
NO — Adding or deleting a whole clause in the clause editor. That needs the "edit the whole document" escape hatch (no add-clause control exists — verified).
PARTLY — Email setup is only discovered after pressing Send ("Queued, not sent"). Nothing warns at workspace creation or before the first share.
PARTLY — "PDF export" is still the browser's print window (exportPDF ends in window.print(), js/views/portal.js:1121); the user must choose "Save as PDF" themselves.

Scenario 1 — Erik will only use Word

Wanjiru drafted the agreement in HaTi with the wizard. Erik exchanges Word files by email. Six rounds. (The full loop below is also exercised by an automated script, test/scenario1.test.js, which passes.)

Round 1 She sends the draft as a Word file

  • She wants to email Erik an editable Word copy.
  • Screen The Word button in the toolbar (js/views/contract.js). One button now — a short dialog explains the one choice: pause editing here while the copy is out, so her edits don't clash with his. Default is on.
  • Steps Three clicks. The file has the title as a real heading, clause numbers intact, and the signature block. Verified by having HaTi's own Word reader open the file it wrote.
This round is now clean. The duplicate button from the last review is gone, and the editing pause is a choice she can read, not a trap she falls into.

Round 2 Erik returns his marked-up file — and the document changes costume

  • She wants to see his changes and take some, not all.
  • Screen Upload returned .docx (uploadWordVersion, js/wordflow.js) → the review window. His two tracked changes are counted, each shown separately with Accept / Reject and a reply box. She accepts the delivery change, refuses the payment change, types "Net-30 stands, or a 2% price increase."
  • Steps About six, all inside the app. His authorship is on the record, not hers.
New finding — the document loses its drafted look here. The moment she accepts, the wizard's styled layout with its fill-in fields is replaced by plain working text (verified by running the code: a template contract's body is not "rich", so the layout-preserving merge from the last round of fixes never applies to it). The app compensates — headings still render bold, clause numbers are set off — but the fill-in fields are gone for good and the document visibly changes character one round in. For a contract pasted in as a formatted document this does not happen; for the built-in wizard templates — her actual case — it does.
Friction 1. Circled: the wizard-drafted layout being replaced by plain text. The layout-preserving engine (richFromTextEdit, js/richdoc.js) already exists — wizard contracts just aren't stored in the format it works on.

Round 3 She counters — and sends Erik a file with no red ink

  • She wants to send her middle position so Erik can see exactly what she changed.
  • Screen Edit → save → the Word button again. The export carries the current wording (the app checks for staleness and regenerates).
  • The gap The file is clean. HaTi can read Word's tracked changes but cannot write them (verified: js/docxwrite.js emits none). Erik — a person who lives on red markup — receives a document that looks untouched. To see her changes he must put her file and his old file side by side in Word and run Compare himself.
This is now the worst friction in Scenario 1. It doesn't block the deal, but every round Wanjiru sends costs Erik a manual Compare in Word, and a counterparty who skips it can miss a change she made. Inside HaTi both sides get beautiful change-tracking; the moment the document leaves for Word, hers goes dark.
Friction 2 — the worst in this scenario. Circled: a clean file where a Word user expects markup. The per-change data already exists (diffBlocks); it is simply never written into the export.

Round 4 Erik returns again, with a brand-new clause

  • She does Upload → review. His inserted clause appears as its own change (a pure insertion block) with its own Accept / Reject. Works.
  • Small note Clause numbers in the file are ordinary text — deliberately, so Word cannot renumber a schedule and break cross-references. The cost: when Erik inserts "clause 5a", any renumbering is his manual job in Word. Reasonable trade, worth knowing.

Round 5 Two changes arrive as email prose, not a file

  • She does Edit → ticks "These changes came from Nordkust Industri AB (received outside HaTi)" → the wording files as a round in his name, waiting for her decision. The record stays truthful about whose words are whose.
  • Steps Four.

Round 6 Agreement — both endings now exist

  • Electronic She sends a single-answer link (untick "keep this link open"); Erik signs with an emailed code — or, on a server with no email service, signs after being told plainly that the signature will be recorded as not independently verified.
  • Paper "Signed on paper instead? File the signed copy here" attaches the scan to this contract: six rounds of history intact, sealed with the scan's own fingerprint, honestly recorded as executed outside HaTi with no electronic signature claimed.
The dead end from the last review is gone. A cross-border deal that ends on paper now lands on the contract it belongs to.

Scenario 1 verdict

7/10   (first review: 2/10 · second review: 6/10)

The single worst friction point: the exported Word file carries no tracked changes. Erik receives clean text every round and must run Word's Compare himself to see what Wanjiru did — the one manual, error-prone step left in a loop that is otherwise fully closed.

Would a real Kenyan SME owner keep using this? Yes. The loop that used to force her out of the product — export, receive markup, decide change by change, counter, sign or file the paper — runs inside it end to end, with an honest record throughout. What stops this being an 8 is the clean export and the document losing its drafted look one round in. Both are polish on a working machine, not holes in it — which is a different situation from six months of reviews ago, and it is fair to say so.

Scenario 2 — Erik negotiates inside HaTi

Same correction as always: there is no counterparty account. "Inside HaTi" means the no-login review page (js/views/portal.js) on one durable link that lasts the whole negotiation. The full loop below is exercised by test/scenario2.test.js, f25 and f29, which drive the real page.

Access How Erik gets in

  • She does Share → name and email (prefilled after the first time) → Send. The link stays live for the whole negotiation by default.
  • He does Clicks it. No account, no password.
The one operational trap left: if the server has no email service connected, the invitation sits in an internal outbox and she must copy the link out by hand. The app now says so honestly — but only after she presses Send. Nothing warns her when the workspace is created, so the first negotiation is where she finds out.
Friction 3. Circled: the moment she currently learns her workspace cannot send email.

Round 1 Erik proposes changes, clause by clause, with reasons

  • He does Propose edits → the document appears as clauses, each with a Change button. He edits the payment clause, writes "Net-60 is our standard" in the Why? box on that clause, changes the delivery clause with its own reason, submits. Untouched clauses are provably untouched — the rebuilt document is character-identical where he didn't edit.
  • Steps About eight. An "edit the whole document instead" escape hatch exists and carries his work across.
New finding: he cannot ask without editing. "Does clause 7 include cold-chain transport?" is a question, not a proposal — and it has no home. His options are the single comment box for the whole round, or a fake edit to a clause he doesn't actually want to change. Every exchange in this product must be dressed as a formal round of proposed text.

Round 2 Wanjiru decides — with his reasons in front of her

  • She does The amber "Changes returned" strip → review. Each change shows Why they asked above its Accept / Reject, with a reply box on that change. She accepts delivery, refuses payment with "Net-30 stands, or a 2% price increase." The record says "partly accepted — 1 of 2 changes", which is what happened.
  • Steps Four clicks and a sentence.
This screen is the best thing in the product — his ask, her decision and her answer sit together on the change they are about, in both directions.

Round 3 She sends the update — and it actually goes

  • She does Send updated version. One click. It emails him (verified against a real server), and when it can't — no mail service, a refused address, a WhatsApp share — it says exactly that and hands her the link, instead of the false "sent" of the last review.
  • He sees The same link, now with a "revised since you last opened it" banner, a one-click comparison, the per-clause conversation, and "Still open between us" showing what he asked, what she said back, and what stands.

Round 4 The gap between rounds

  • What he wants To answer her "Net-30 stands, or 2%" with "would you take Net-45?" — a sentence, not a redraft.
  • What he must do Open a new formal round: edit the clause to Net-45, attach the reason, submit. It works — the scenario script does exactly this — but a one-line reply costs a full propose-review-decide cycle each time.
The negotiation only speaks in formal rounds. Between her decision and his next proposal there is no conversation channel; the discussion happens in the metadata of edits. For price haggling — the most common exchange there is — that is a heavyweight costume for a light sentence.
Friction 4 — the worst in this scenario. Circled: the propose-review-decide machinery that every one-line reply must pass through.

Round 5 The money round

  • He does Request changes → proposes a lower annual value with a comment.
  • She does Accepts. The value updates, and any internal approval already collected is correctly voided — she must be re-approved before signing. Honest, one extra loop.

Round 6 Acceptance, signature, seal

  • He does Accept the wording (without signing) — a real distinction — then signs: with email configured, a 6-digit code; without it, a plain warning first, and the signature recorded everywhere as not independently verified.
  • She does Ticks intent-to-sign, signs. The exact text is frozen and sealed, and the history tells the whole story: who asked for what, why, what was decided, and what was said back — per clause.

Scenario 2 verdict

7/10   (first review: 5/10 · second review: 5/10)

The single worst friction point: every exchange must wear the costume of a formal round. There is no way to ask a question about a clause, or answer a counter-offer with a sentence, without proposing edited text and triggering the full review cycle. The negotiation machinery is now excellent — and it is the only room in the house.

Would a real Kenyan SME owner keep using this? Yes — and this time without the caveats that ended the last two reviews. The silent failure is gone, both sides see the same conversation, and the deal can end by e-signature or on paper without losing its history. The remaining risk is operational, not structural: a workspace that never configures email will ferry every link by hand and produce weaker signatures, and the app only mentions this after the fact. Fix the talking gap and the email onboarding, and this is an 8–9.

What to fix, in order

Eight items, ordered by pain removed per unit of work. Sizes: small = days, medium = 1–2 weeks, large = several weeks. The mobile/WhatsApp counterparty portal is deliberately not on this list.

1. Export Word files with the changes marked in red

medium

Change: when a contract has a previous round, write the differences into the exported file as real Word tracked changes — new words as insertions, removed words as strike-outs — so Erik opens it and sees the markup he lives on. HaTi already computes exactly what changed each round; it just never writes it into the file.

Why it hurts today: every round Wanjiru sends looks untouched. Erik must run Word's Compare himself, and a counterparty who skips that step can miss a change. It is the last manual, error-prone step in Scenario 1.

2. Let both sides discuss an open point without a formal round

medium

Change: a reply box on each "still open" point and on each clause, both directions, without requiring edited text. Proposing wording stays the formal act; talking about it stops being one.

Why it hurts today: "Would you take Net-45?" costs a full propose-review-decide cycle. Price haggling — the most common exchange in any negotiation — is the heaviest thing to do in the product.

3. Warn about missing email at setup, not at Send

small

Change: check for an email service when the workspace is created and show a plain banner until one is connected: links and signing codes cannot be delivered without it, here is the 2-minute setup. Repeat the warning before the first share, not after it.

Why it hurts today: the first negotiation is where she discovers the invitation never left. Everything downstream — update notices, signing codes, signature strength — quietly depends on this one setting.

4. Keep the wizard-drafted look through negotiation

medium

Change: store contracts created by the wizard as formatted documents from the start, so the layout-preserving merge that already works for pasted templates applies to them too.

Why it hurts today: at the first accepted round, the styled draft with its fill-in fields becomes plain working text. The document Wanjiru signs at round six looks meaningfully worse than the one she drafted at round zero — and this is the default path every wizard user is on.

5. Let the clause editor add and remove whole clauses

small

Change: an "add a clause here" control between clauses, and a "propose deleting this clause" option on each — feeding the same reassembly that already proves itself byte-exact.

Why it hurts today: Erik can change any clause but cannot propose a new one or the removal of one without dropping into the whole-document text box — the exact surface the clause editor exists to retire.

6. Tell Erik his proposal landed and is being looked at

small

Change: after he submits, show on his page "Delivered to Wanjiru Catering Ltd — you'll get an email when they respond", and update it when the round is opened on her side. The mirror of the seen-state she already has.

Why it hurts today: after submitting, his page goes quiet until she reshapes the deal. He cannot tell "being considered" from "lost", which is the same silence problem the last review fixed for her side only.

7. Say what changed in the update email

small

Change: the "contract updated" email currently says only that it changed (verified: the message body names the contract and the link, nothing else). Add one line: "2 changes: payment terms, delivery window — 1 of your asks adopted."

Why it hurts today: a busy procurement manager triages by inbox. "Something changed" competes badly with everything else in it; "your payment ask was adopted" gets clicked.

8. A real PDF file, not the print window

medium

Change: "Export PDF" currently opens the browser's print window and relies on the user choosing "Save as PDF" (exportPDF ends in window.print()). Produce an actual PDF file, the way the Word export now produces an actual Word file.

Why it hurts today: the print window varies by browser and printer setup, headers and page numbers leak in, and "where did the PDF go" is a support question waiting to happen — including in a demo.

Where this leaves the product

Three reviews in, the shape of the findings has changed. The first review found a product whose best engineering was switched on for the wrong side of the deal. The second found the counterparty's half broken and untested. This one found no broken promises and no silent failures — every claim the app makes to its users checked out against the running code, which is a sentence that could not have been written before.

What remains is a working machine with two real gaps: the document that leaves for Word carries no red ink, and the negotiation has no voice quieter than a formal round. Items 1 and 2 are those gaps. Items 3–8 are the polish that turns a tool people use into one they stop noticing.

Method note: this review is based on reading the source at commit 01cfb6e and verifying each claim by execution — the wizard-contract flattening was reproduced by running acceptProposedRound on a template-shaped contract, the clean export by inspecting what js/docxwrite.js emits, and the working flows via the automated scripts that drive the real screens (test/scenario1.test.js, test/scenario2.test.js, f24, f25, f29 — all passing, 434 checks, twice on clean copies). Step counts come from the actual click paths. No feature described here was assumed from what a contract tool usually has.
