HaTi — the same two negotiations, run a fourth time on today's code

A user-experience review of the HaTi contract platform (repo youngmbg21-cmyk/mkataba-clm), based on reading and running the source at commit ba6534d, 26 July 2026. The two problems the last review called the worst have both been fixed. I checked them by running them, not by trusting the commit messages — including on the exact kind of contract the last review admitted its own tests had never used. Six real problems remain. Four are new to this pass, and two of those are faults in the work that just landed.

The two people in the story

Wanjiru owns a small catering company in Nairobi. She drafted a 12-month supply agreement inside HaTi using the built-in "Raw Material Supply Agreement" template and the guided wizard (js/wizard.js). This matters more than it sounds. A contract drafted this way is not saved as a document at all. It is saved as a recipe — the template, plus the answers she typed — and the document is rebuilt on screen each time she opens it (docBody, js/views/contract.js).

Erik is a procurement manager at a mid-size Swedish firm. In Scenario 1 he only uses Microsoft Word with tracked changes (Word's way of showing every edit in red), over email. In Scenario 2 he works inside HaTi.

What the app actually has today

The honest inventory, taken from the code — not from what a contract tool usually has:

YES — One-click export of any contract as a real Word file, with a plain choice about pausing edits while the copy is out (openWordExportModal).
YES — The exported Word file now carries her changes in red.new Insertions and strike-outs are written as genuine Word tracked changes, signed with her company's name (js/docxwrite.js). Checked: HaTi's own Word reader finds them, and accepting them all produces exactly the wording HaTi holds.
YES — Upload the counterparty's marked-up Word file onto the same contract; his changes are counted and filed as a round in his name (js/wordflow.js).
YES — Accept or reject each change separately, see why they asked against each one, and reply on that change (reviewProposedRound).
YES — A message channel that is not a formal round.new Either side can ask or answer a question without proposing new wording (js/discuss.js). Checked: sending one opens no round, saves no new version, changes not a character of the contract, and leaves the link still answerable.
YES — The counterparty edits clause by clause, with a "Why?" box per change, on one link that lasts the whole negotiation (js/views/portal.js).
YES — "Send updated version" genuinely emails him, and says plainly when it could not.
YES — A paper-signed scan files onto its own contract, history intact, honestly labelled "executed outside HaTi".
NO — A drafted contract that reads like a contract. Dates leave as 2026-08-01 and money as KES 4800000 in every copy that leaves the screen: the Word file, the counterparty's page and the signed record. Read straight out of the exported file.
NO — A wizard-drafted contract that keeps its fill-in blanks. Checked by running the code: six blanks before the first accepted round, zero after — and the history says nothing about it.
NO — A reply box where the conversation actually is. The "Still open between us" card has no way to answer; the new message box is a separate panel further down the page.
NO — Any sign, anywhere outside that one contract's page, that a question is waiting for her. Nothing on the dashboard or the work queue counts them.
NO — A way for Erik to see that his proposal arrived and is being read.
NO — Adding or deleting a whole clause in the clause editor. No such control exists.
PARTLY — Email setup is still only discovered after pressing Send. The server knows the answer but never passes it to the app at sign-in. That same sign-in call already reports whether the Copilot features are set up; email was left out of it.
PARTLY — "PDF export" is still the browser's print window (exportPDF ends in window.print(), js/views/portal.js:1167).

Scenario 1 — Erik will only use Word

Wanjiru drafted the agreement in HaTi with the wizard. Erik exchanges Word files by email. Six rounds.

Round 1 She sends the draft as a Word file — and it goes out looking half-finished

  • She wants to email Erik an editable Word copy.
  • Screen The Word button in the toolbar (js/views/contract.js) → a short dialog.
  • Steps Three clicks. The file is a genuine Word document: title as a real heading, clause numbers intact, signature block present. I confirmed this by having HaTi's own Word reader open the file HaTi wrote.
New finding — the document reads like a database record, not an agreement. Her contract opens with "This Raw Material Supply Agreement is made on 2026-08-01", and later "the estimated annual contract value is KES 4800000". Those are the raw values as a computer stores them. On her own screen this is hidden, because each blank is a form box that the browser tidies up for display. The moment the document leaves that screen — into Word, into the counterparty's page, into the signed record — the tidying stops and the raw values show through. I read them out of the exported file itself. This is the first thing Erik sees, and it happens on the default path that every wizard user is on.
Friction 1 — the worst in this scenario. Circled: the raw values as they arrive in Erik's Word file. The same text is what the counterparty's page shows, and what the signature seal is taken over.

Round 2 Erik returns his marked-up file — and the blanks disappear for good

  • She wants to see his changes and take some, not all.
  • Screen Upload returned .docx (uploadWordVersion) → the review window. His changes are counted and listed separately, each with Accept / Reject and a reply box.
  • Steps About six, all inside the app. His authorship is on the record, not hers.
Confirmed, and worse than the last review reported. I ran the real code on a real wizard-drafted contract. Before she accepts, the document has six fill-in blanks. The instant she accepts, it has zero, and the contract stops being a recipe and becomes a block of plain working text. That much the last review found. What it missed: the history says nothing about it. The record shows "Round 1 proposed edits from Nordkust accepted — adopted as v2", and not one word about the document changing character. HaTi does warn about this when it happens to an uploaded document. On the wizard path — the default path — it is silent.
Friction 2. Circled: the blanks, gone. Both the loss and the silence about it are on the default path — this is what happens to the contract Wanjiru actually drafted.

Round 3 She counters — and this time Erik sees red ink

  • She wants to send her middle position so Erik can see exactly what she changed.
  • Screen Edit → save → the Word button. The dialog now says plainly that this copy will carry her changes in red, in her company's name, and offers to turn that off.
  • Steps Four.
The worst problem in the last review is genuinely fixed. I checked it on a wizard-drafted contract — the case the last review's own tests had never covered — and the export carried two insertions and one strike-out, correctly attributed to her company rather than to the software. I also checked the property that matters most: pressing "Accept All" in Word produces exactly the wording HaTi holds, so the file cannot quietly invent contract text. Erik no longer has to run Word's Compare by hand.
One caution worth knowing. HaTi decides what to mark in red by remembering the last copy that left the building, and it records that on every Word download — including one she takes purely to read on her own laptop. If she does that, HaTi will assume Erik is holding a copy he never received, and the next file she sends him will mark the wrong things. The fix is one question in the dialog. Today there is no question.

Round 4 Erik returns again, with a brand-new clause

  • She does Upload → review. His inserted clause appears as its own change with its own Accept / Reject. Works.
  • Small note Clause numbers are ordinary text on purpose, so Word cannot renumber a schedule and break cross-references. The cost: if Erik inserts "clause 5a", renumbering is his manual job. A reasonable trade, worth knowing.

Round 5 Two changes arrive as email prose, not a file

  • She does Edit → ticks "These changes came from Nordkust Industri AB (received outside HaTi)" → the wording files as a round in his name, waiting for her decision.
  • Steps Four. The record stays truthful about whose words are whose.

Round 6 Agreement — both endings exist

  • Electronic She sends a single-answer link; Erik signs with an emailed code — or, on a server with no email service, signs after being told plainly that the signature will be recorded as not independently verified.
  • Paper "Signed on paper instead? File the signed copy here" attaches the scan to this contract, six rounds of history intact.
And the document he signs still says "made on 2026-08-01". The formatting problem from round 1 stops being cosmetic here: it is baked into the sealed record and into the PDF.

Scenario 1 verdict

8/10   (first: 2/10 · second: 6/10 · third: 7/10)

The single worst friction point: the drafted contract reads like a database record rather than an agreement. "Made on 2026-08-01" and "KES 4800000" are in every copy that leaves her screen, from round one through to the sealed signature. It is the first impression a Swedish procurement manager forms of a Kenyan supplier, and it is entirely avoidable.

Would a real Kenyan SME owner keep using this? Yes. The round trip that used to force her out of the product now runs inside it from end to end, and the red-ink export closes the last manual step. What holds it back from a 9 is that the document itself degrades: it looks unfinished on day one, and loses its blanks on day two with nothing on the record to say so.

Scenario 2 — Erik negotiates inside HaTi

The same correction as always: there is no counterparty account. "Inside HaTi" means the no-login review page (js/views/portal.js) on one link that stays live for the whole negotiation.

Access How Erik gets in

  • She does Share → name and email (prefilled after the first time) → Send.
  • He does Clicks the link. No account, no password.
Unchanged from the last review, and it now matters more. If the server has no email service connected, the invitation sits in an internal outbox and she must copy the link out by hand. The app says so honestly — but only after she presses Send. I checked why. The server does work this out, and hands it over on several screens, but it is never included in the one call the app makes when she signs in. That call already reports whether the Copilot features are set up. Email was simply left out of it.

Round 1 Erik proposes changes, clause by clause, with reasons

  • He does Propose edits → the document appears as clauses, each with a Change button and a Why? box. He edits payment and delivery, submits.
  • Steps About eight. Clauses he did not touch are provably untouched.
Still no way to add or remove a whole clause. He can change any clause but cannot propose a new one, or the deletion of one, without dropping into the "edit the whole document" text box — the exact surface the clause editor exists to retire.

Round 2 Wanjiru decides — with his reasons in front of her

  • She does The amber "Changes returned" strip → review. Each change shows Why they asked above its Accept / Reject, with a reply box on that change. She accepts delivery, refuses payment with "Net-30 stands, or a 2% price increase."
  • Steps Four clicks and a sentence.
This screen is still the best thing in the product. His ask, her decision and her answer sit together on the change they are about, in both directions.

Round 3 He wants to answer with one sentence — and now he can, but not where he is standing

  • What he wants To answer "Net-30 stands, or 2%" with "would you take Net-45?" — a sentence, not a redraft.
  • What exists now A real message channel. I confirmed it does exactly what it should: no round is opened, no version saved, the contract's wording untouched to the character, and the link still answerable afterwards.
  • What he must actually do Read her refusal in the "Still open between us" card. Find no way to answer there. Scroll past two more panels to a separate message box. Open a dropdown of seven options. Notice the default is "The contract generally", not the point he was just reading. Pick the right line. Type. Send.
New finding — the reply is not where the conversation is. I rendered the real page and read it. The "Still open between us" card contains no reply box and no reply button. Its instruction is still "press Propose edits if you want to come back on it" — the six-step route the new channel was built to replace. The light channel exists. It just is not where anybody is standing when they need it.
Friction 3. Circled: the card that carries the argument and offers no way to answer it, and the dropdown that defaults to the wrong thing.

Round 4 His question sits unread

  • He does Sends "Would you take Net-45?" The page confirms it went.
  • She does Nothing, because nothing tells her.
New finding — a waiting question is invisible. I searched the whole app. Nothing on the dashboard, the work queue or the contract list counts unanswered messages. The only two ways she finds out are an email, or opening that one contract and scrolling. And email is the setting most workspaces have not configured — the very problem three panels above. Put those together and on a fresh workspace there is no alert at all. The message is stored safely and displayed correctly; it is simply somewhere nobody is looking. A channel nobody watches is slower than the formal round it replaced, because a formal round at least raises an amber strip on her screen.
Friction 4 — the worst in this scenario. Circled: the moment the question stops moving. The "Decisions due" card on her dashboard already exists and already gets read. It simply does not count messages.

Round 5 The money round

  • He does Request changes → proposes a lower annual value with a comment.
  • She does Accepts. The value updates, and any internal approval already collected is correctly cancelled — she must be re-approved before signing. Honest, one extra loop.
He still cannot tell "being considered" from "lost". After he submits anything, his page shows a green tick and then goes quiet until she reshares. There is no "delivered", no "opened by them", no "you'll hear when they respond". She has all of that about him. He has none of it about her.

Round 6 Acceptance, signature, seal

  • He does Accept the wording (without signing) — a real distinction — then signs: with email configured, a 6-digit code; without it, a plain warning first, and the signature recorded everywhere as not independently verified.
  • She does Ticks intent-to-sign, signs. The exact text is frozen and sealed, and the history tells the whole story: who asked for what, why, what was decided, and what was said back — per clause.

Scenario 2 verdict

8/10   (first: 5/10 · second: 5/10 · third: 7/10)

The single worst friction point: a question can wait unseen. The light channel is real and correctly built, but nothing outside that one contract page says a question is waiting, and the email that would say so is the setting most workspaces have not configured. The product built a doorbell and did not connect it to a bell.

Would a real Kenyan SME owner keep using this? Yes. Both sides now see the same conversation, a sentence no longer costs a full round, and the deal can end by e-signature or on paper without losing its history. What is left is about where things are put, not about whether they work — a much better class of problem than this product had six months ago. Connect the alert, move the reply box to where the argument is, and this is a 9.

What to fix, in order

Eight items, ordered by pain removed per unit of work. Sizes: small = days, medium = 1–2 weeks, large = several weeks. The mobile/WhatsApp counterparty portal is deliberately not on this list.

1. Write dates and money the way a contract writes them

small

Change: when the document is turned into text — for Word, for the counterparty's page, for the PDF, for the signature seal — write dates as 1 August 2026 and money as KES 4,800,000, instead of the raw values the computer stores.

Why it hurts today: every copy that leaves her screen says "made on 2026-08-01" and "KES 4800000". It is the first impression the counterparty forms, it is what he marks up, and it ends up inside the sealed signature record. Looking professional here costs almost nothing. Not doing it costs a great deal.

2. Warn about missing email on day one, not at Send

small

Change: include "is email set up?" in the information the app already fetches when she signs in, and show a plain banner until it is connected. Repeat it in the Share window before she presses Send.

Why it hurts today: the first negotiation is where she discovers the invitation never left. Everything quiet depends on this one setting — invitations, update notices, signing codes, the strength of the signature itself, and now the new questions channel too. The server already works this out and reports it on several other screens. It is simply missing from the one call that would let the app say it early.

3. Count waiting questions where she already looks

small

Change: add unanswered questions to the "Decisions due" card on the dashboard and to the contract list, the same way returned changes already appear. Do the mirror on the counterparty's page.

Why it hurts today: the new message channel works perfectly and is watched by nobody. The only alerts are an email that most workspaces cannot send, and opening that one contract. A question can sit for a week while each side believes the other is thinking about it.

4. Put the reply box where the argument is

medium

Change: a reply box directly inside each "Still open between us" point and on each clause, both directions, with no dropdown to choose from — the point you are reading is the point you are answering. The separate panel can stay for a general remark.

Why it hurts today: the card that carries the disagreement still tells the reader to "press Propose edits", which is the six-step route the message channel was built to avoid. To use the light route he must scroll away from what he is answering and pick it out of a seven-item list whose default is the wrong one. Half the feature landed.

5. Keep the wizard-drafted document whole — and say so if it changes

medium

Change: the first time a wizard-drafted contract is edited, or a round is accepted on it, turn it into a real saved document that keeps its blanks, instead of flattening it into plain text. Until that is done, at the very least write a line in the history saying the document changed character.

Why it hurts today: six fill-in blanks become zero at the first accepted round, permanently, and the history does not mention it. This is the default path for every wizard user. The layout-keeping machinery already exists and is already proven for uploaded documents — wizard contracts simply never reach it.

6. Tell Erik his proposal arrived and is being read

small

Change: after he submits, show on his page "Delivered to Wanjiru Catering Ltd — you'll get an email when they respond", and update it when she opens the round. The mirror of the seen-state she already has about him.

Why it hurts today: he gets a green tick and then silence until she reshares. He cannot tell "being considered" from "lost" — the same silence problem an earlier review fixed for her side only.

7. Let the clause editor add and remove whole clauses

small

Change: an "add a clause here" control between clauses, and a "propose deleting this clause" option on each — feeding the same rebuild that already proves itself exact.

Why it hurts today: the counterparty can change any clause but cannot propose a new one, or the removal of one, without dropping into the whole-document text box — the exact surface the clause editor exists to retire.

8. A real PDF file, not the print window

medium

Change: produce an actual PDF file, the way the Word export now produces an actual Word file. Build it in-house: this app deliberately carries no outside code libraries, which is why it is cheap to host and hard to break, and the Word writer already proves the approach works.

Why it hurts today: "Export PDF" opens the browser's print window and relies on the user knowing to choose "Save as PDF". The result varies by browser and printer, page headers leak in, and "where did the PDF go?" is a support question waiting to happen — including in a demo.

Where this leaves the product

Four reviews in, the findings have changed shape again. The first found a product whose best engineering was switched on for the wrong side of the deal. The second found the counterparty's half broken and untested. The third found a working machine with two real holes in it. This one found both holes properly filled — checked by running them, not by reading the commit messages — and a different kind of problem underneath.

What is left is almost entirely about placement. The message channel is correct and unwatched. The reply box is correct and in the wrong panel. The email setting is known by the server and never said out loud early enough. The document is assembled correctly and written out carelessly. None of these is a hole in the machine. All of them are things put where nobody is standing.

Two of the six problems in this review are faults in the work that landed since the last one. That is worth saying plainly rather than quietly: shipping the right feature into the wrong place is the failure mode this product now has, and it will not show up in a test suite. Every one of those tests passes.

Method note: this review is based on reading the source at commit ba6534d and checking every claim by running it. The red-ink export and the loss of the fill-in blanks were both reproduced on a contract built the way js/wizard.js actually builds one — no saved document, no formatting marker — because the previous review admitted its own tests had used a convenient stand-in instead, and missed a real fault as a result. The raw dates and money were read out of the exported Word file itself. The missing reply box and the seven-option dropdown were read off the counterparty page as it renders. The absence of any question counter was established by searching the dashboard and work-queue code. The existing automated suite (476 checks) passes in full — which is rather the point: not one problem in this review is a failing test.
